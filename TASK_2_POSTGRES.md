# Task 2 — Account database: MySQL to PostgreSQL

Branch: `task-2-postgres`, based on Task 1. The migration plan was shown before schema edits. Task 3 (stored sessions) has not started; JWT cookies and scrypt are unchanged.

## Changes

- Added `pg` and development-only `@types/pg`; removed `mysql2`.
- Drizzle uses `node-postgres` and `pg-core`. One reusable pool per process (maximum 10 connections, 10-second connection acquisition timeout, 30-second idle timeout).
- All seven tables and their existing column names remain: users, localAccounts, learningStates, workspaces, interviewQuestions, studySessions, skillProgressHistory. JSON stays text to preserve serialized workspace content; no new foreign keys or data cleanup silently changes legacy rows.
- Auto-increment columns become PostgreSQL GENERATED BY DEFAULT AS IDENTITY, permitting explicit historical IDs. The user role is a PostgreSQL enum. Timestamps use timestamptz. A separate trigger migration preserves automatic updatedAt changes, including SQL outside Drizzle, while respecting explicit historical timestamps.
- Upserts specify conflict keys; account insertion uses RETURNING id; revision checks use rowCount; unique-violation SQLSTATE 23505 produces the existing conflict response.
- New migrations and metadata are in `drizzle/postgres`. The old MySQL migration files remain untouched for history/rollback; the PostgreSQL runner never uses them.

## Migrations and Neon configuration

`DATABASE_URL` is the application's PostgreSQL URL. For Neon, use a TLS connection string with `sslmode=verify-full`; no code disables certificate verification. A pooled Neon endpoint can serve the application. Set optional `DATABASE_MIGRATION_URL` to the direct/unpooled endpoint for migration operations. The same database must be selected in both URLs. Secrets belong in the deployment environment, never Git.

Run `pnpm db:migrate` against an empty PostgreSQL database to apply:

1. `0000_mature_celestials.sql`: generated by drizzle-kit; seven tables, identity sequences, enum and indexes.
2. `0001_touch-updated-at.sql`: drizzle-kit custom migration; timestamp function and four triggers.

`pnpm db:generate` generates further schema migrations; `db:push` continues to be an alias for applying committed migrations, not destructive schema push.

## Existing MySQL data: controlled transfer procedure

Schema migrations create the PostgreSQL structure; they do **not** copy MySQL data. No existing or production database was accessed during this task.

1. Retain a deployable build of commit `dcbaac0` and its locked dependencies. Back up MySQL and verify restoration into a separate database before the cutover window.
2. Inventory row counts and all seven tables. Check for zero/invalid dates, embedded NUL characters, oversized values, duplicate normalized account emails, and orphan owner IDs. PostgreSQL text comparison differs from MySQL collation; application sign-in normalizes email, but legacy non-normalized addresses require an explicit reviewed resolution rather than silent conversion.
3. Freeze writes to the MySQL application; disable account saves/registrations during the final export. Export using a consistent snapshot and MySQL session timezone `+00:00`. Protect exports as credentials/personal data: they contain password hashes, profiles and evidence.
4. Apply the PostgreSQL migrations to a new empty destination. Export/import each table with an explicit column list matching `drizzle/schema.ts`, using a CSV or parameterized ETL tool that preserves SQL NULL separately from empty strings, embedded newlines, UTF-8, and JSON strings. Include original IDs and all timestamps (explicit UTC offsets). Do not execute a MySQL SQL dump directly against PostgreSQL.
5. Load users first, then localAccounts and learningStates, then the four legacy/history tables, in one PostgreSQL transaction. Preserve passwordHash bytes exactly; never rehash or regenerate user/openId identifiers. Keep createdAt, updatedAt, lastSignedIn, recordedAt and revision unchanged. Imported timestamp fields must be supplied explicitly rather than taking defaults.
6. Advance each identity sequence after importing. For users, workspaces, interviewQuestions, studySessions and skillProgressHistory, use `pg_get_serial_sequence` with the correctly quoted table name, then `setval(sequence, max(id), true)` when nonempty. For an empty table use `setval(sequence, 1, false)`. Check the next generated ID exceeds the imported maximum.
7. Before accepting writes, compare row counts, primary-key sets, owner relationships, exact hashes/JSON values and UTC timestamp values between source and destination. Verify existing-account login, Arabic content, saved progress, revision conflicts, and legacy data. Take a PostgreSQL backup at this checkpoint.
8. Switch application DATABASE_URL to the validated Neon database and deploy this branch. Keep the MySQL snapshot read-only. Run smoke checks before lifting the write freeze.

Rollback before new PostgreSQL writes: restore the previous application build and MySQL connection, then re-enable writes there. If new writes have already been accepted in PostgreSQL, freeze again and reconcile those changes before rollback; simply changing the connection would lose them. Never run the historical MySQL migrations against PostgreSQL.

This is the cutover procedure, not a claim that a live source-data transfer or Neon deployment has been performed. No source database/Neon credentials were supplied or needed for local validation.
